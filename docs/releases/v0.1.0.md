# ParcelPulse v0.1.0

The first tagged version of ParcelPulse, and the engineering baseline of this
repository: the four originally independent components, integrated here with
their histories, verified together, with CI.

It runs locally with one command. **Nothing is deployed.**

## What it does

- **Register shipments** by tracking number and carrier, from the dashboard or
  the API.
- **Ingest carrier webhooks**, signed with HMAC-SHA256, into a per-shipment
  timeline.
- **Duplicate webhooks are safe.** A redelivered event is acknowledged and
  changes nothing: no second event, no second status change, no second
  notification.
- **Out-of-order events are safe.** The current status is derived from what the
  events mean and when the carrier says they happened. A late event joins the
  timeline at its place and cannot move a shipment backwards. The carrier's
  event time and ParcelPulse's receipt time are both kept.
- **Email notifications** for out for delivery, delivered and delivery
  exception, sent asynchronously with retries, once per event. Preferences are
  set per shipment.
- **Dashboard**: tracking search, shipment list with status filter, shipment
  page with timeline, notification preferences and history.
- **Carrier simulator** for development and testing, able to send events in
  order, repeated, delayed, swapped, with exceptions, with retries and in
  bursts.
- **Operations**: liveness and readiness endpoints, structured JSON logs with
  correlation IDs from webhook to email, Prometheus metrics on the API.

## How it was verified

As required by [../release-process.md](../release-process.md): every component's
lint, type checks and test suites; the stack started from an empty database
with migrations applied from zero; the end-to-end smoke test; the dashboard
against the real API; and the five CI workflows on the tagged commit. The
results of that validation are recorded in issue #7 and in
`docs/PARCELPULSE_B0_BASELINE.md`, which is added after the tag.

## Running it

```powershell
cd infra
docker compose up --build        # builds api/, worker/ and web/ from this checkout
docker compose run --rm smoke    # end-to-end check
```

See [../local-development.md](../local-development.md).

## Known limitations

- **No authentication.** The dashboard and the API's shipment endpoints are
  open to anyone who can reach them. Do not expose them to the internet. (#12)
- **No real carrier.** The only supported carrier is the simulator. (#13)
- **Not deployed**, and no deployment pipeline. See
  [../deployment.md](../deployment.md). (#20)
- **One case can send a notification twice:** the worker dying after the mail
  server accepted a message and before that was recorded. The message carries a
  stable Message-ID. (#10)
- Notifications that run out of attempts stay `FAILED`; there is no re-send.
  (#15)
- A delivered or returned status cannot be corrected by a later event.
- `webhook_receipts` and `notifications` are never pruned. (#14)
- The delivery estimate is the carrier's; ParcelPulse does not compute one.
- Webhook ingestion throughput did not increase with concurrency in the first
  load test ([../load-testing.md](../load-testing.md)). The cause is not
  known. (#17)
- No browser test suite for the dashboard. (#11)
- The contracts between components are mirrored by hand; only the full-stack
  smoke test checks them together. (#18 for the REST contract)
- No Slack workspace has been set up; the channel bootstrap has never run
  against a real workspace. (#19)
- Pull requests have had no review approvals so far: a single account opened
  and merged them.
- Email only; English only.
